## Project Audit (risk-first) — Design

**Goal:** Провести полный аудит backend-проекта, подготовить отчёт и PR(ы) с недостающими тестами/фикcами, так чтобы CI реально запускал тесты и регрессии ловились автоматически.

**Architecture:** Начинаем с risk-first аудита: безопасность и критичные точки входа → API контракты и права доступа → бизнес-логика сервисов → надёжность/observability → CI/quality gates. Изменения поставляются небольшими PR’ами с тестами и проверками.

**Tech Stack:** Django 5.1, DRF, Postgres, Redis, Celery, pytest + pytest-django, Poetry, GitHub Actions, Docker.

---

### Scope

- **Security / secrets**
  - Секреты в репозитории и конфигурации (пример: `private-key.pem` в корне).
  - CSRF/redirect safety: `/post_login_redirect/` и allowlist origins.
  - CORS/CSRF домены, cookie параметры (prod vs debug), `SESSION_COOKIE_SAMESITE=None` + `Secure=True`.
  - Права и авторизация: DRF permissions (`IsContractor`, группы), доступ к данным только по владельцу.
  - Чувствительные эндпоинты: `/qz/sign/` (CSRF exempt), `/qz/cert/`.

- **API (DRF)**
  - Контракты и статусы ответов.
  - Валидация сериализаторов (в т.ч. даты, обязательные поля).
  - Ограничение данных по пользователю/группе.

- **Business logic**
  - `orders/services/*` (генерация Excel и т.п.): корректность, edge cases, стабильность.

- **Reliability**
  - `/health/` поведение при недоступности Postgres/Redis/Celery.
  - Поведение при исключениях и качество логирования.

- **CI / Quality**
  - Включить запуск `pytest` в CI (сейчас workflow делает только migrations).
  - Минимальные quality-gates: тесты обязательны; линтеры/форматтеры — опционально отдельным PR.

### Deliverables

#### 1) Audit report (in-repo)

Файл: `docs/audit/2026-03-10-project-audit.md`

- Summary (5–10 пунктов).
- Findings таблица:
  - `Severity (blocker/high/medium/low) | Area | What | Risk | Fix | PR link`
- Test coverage map: что покрыто тестами/не покрыто.
- CI gap: что проверяется/не проверяется в пайплайне.
- Follow-ups: следующий backlog после PR(ов).

#### 2) PRs

- **PR1 (минимум, чтобы проект стал проверяемым):**
  - Запуск `pytest` в GitHub Actions.
  - Минимальная тест-инфраструктура (`tests/`, `conftest.py`, фикстуры пользователей/групп).
  - Smoke/безопасностные тесты:
    - `post_login_redirect`: разрешён/запрещён редирект; отсутствие `url`.
    - `qz_sign`: пустое тело → 400; метод только POST; (риски CSRF exempt — в отчёт).
    - DRF permissions: contractor видит только свои заказы; чужие недоступны.

- **PR2 (по приоритетам из отчёта):**
  - Тесты сериализаторов `orders`/`labels`/`system`.
  - Тесты сервисов (Excel): минимум “не падает” + проверка ключевых данных в файле.
  - Малые безопасные улучшения (без изменения бизнес-логики “на глаз”), если нужны для тестируемости.

---

### Non-goals (явно вне объёма первой волны)

- Крупные рефакторинги архитектуры без конкретного инцидента/ошибки.
- Изменение бизнес-правил без подтверждённого бага/спеки.
- Оптимизации производительности без профилирования и конкретной метрики.

---

### Safety / Constraints

- Не выполнять destructive операции с БД (все тесты через test DB).
- Не раскрывать секреты; любые найденные секреты фиксировать в отчёте и предлагать безопасное устранение.
